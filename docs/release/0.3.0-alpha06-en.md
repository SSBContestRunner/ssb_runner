# SSB Runner 0.3.0-alpha06 Release Notes

Version: `0.3.0+300006`

**This is still an alpha preview of 0.3.0, not a stable release.** It fixes the
Windows shutdown hang that failed `0.3.0-alpha05`'s Windows smoke test: closing
the window while the audio engine was still initialising left the process
running in Task Manager with no window. The database schema and the event-log
format are unchanged, so training history and settings survive the upgrade as
is. Use `0.2.1` if you are logging a real contest.

Upgrading from `0.3.0-alpha05` is a plain over-install.

## Windows: closing during startup no longer leaves a background process

- **Symptom.** In the first few hundred milliseconds after the window appears
  (while SoLoud was still opening the audio device), closing the window made it
  disappear while the process stayed in Task Manager forever. Nothing crashed
  and nothing more was logged: the process was stuck inside `ExitProcess`.
- **Cause.** `SoLoud.isInitialized` stays `false` for the whole initialisation,
  so the old exit path skipped the deinit and answered the exit request. The
  engine was torn down normally (58 ms in the captured trace) and `wWinMain`
  returned, but `ExitProcess` then runs every DLL's `DllMain(DLL_PROCESS_DETACH)`
  and the SoLoud plugin waits there on a kernel object that only its — now
  gone — initialisation thread could have signalled. The Dart fallback timer
  cannot help: the Dart VM is already shut down at that point.
- **Fix.** The exit path now tracks the initialisation. It waits up to 2 s for
  an in-flight initialisation to settle, always disposes the engine (bounded,
  whether it is running, never started or failed to start), and only answers
  the exit request when the engine is in one of the two definite states: never
  initialised, or fully disposed. Any other outcome terminates the process
  directly, which skips CRT and DLL teardown instead of hanging inside it.
- **The boot sequence stops dispatching new steps** once the close request
  arrives, so closing during startup no longer races the remaining startup
  steps.
- The failure only reproduced when the close landed inside the ~30–400 ms
  initialisation window, which is why it appeared intermittently and only in
  CI.

## Windows: native exit watchdog

- **A native watchdog now covers the phase Dart cannot reach.** It is armed on
  `WM_CLOSE`, waits 5 s and terminates the process if `ExitProcess` itself is
  still running. The existing Dart fallback still covers a stuck cleanup; the
  two together bound the whole exit path to 5 s.
- The watchdog event and thread are created lazily when the close arrives, so
  startup cost and the thread count of a normal run are unchanged.

## Exit diagnostics

- The exit path writes a small synchronous trace (`exit_<pid>.log`) next to the
  native startup timeline, with marks such as `enter`, `settled`,
  `deinit_done`, `answering_exit`, `hard_exit_*` and `fallback_fired`. The
  regular application log is buffered, so it cannot prove what happened after
  the window disappeared.

## Windows smoke test: close timing is swept

- The smoke test now closes the window at several delays instead of one, so the
  "close while audio initialises" window cannot silently reopen.
- A hang now gets a minidump and thread stacks captured before the process is
  killed, instead of only the fact that it was still alive.

## Tooling: the analyzer gate now includes info-level lints

- CI runs `flutter analyze --fatal-infos`; info-level lints are now gating, so
  this debt cannot pile up again.
- 51 `prefer_initializing_formals` infos, surfaced by the Dart 3.13 private
  named parameters, are fixed without changing a single call-site argument
  name, and the unreferenced `CQ_WPX` constant is removed.
- The tree was reformatted once with the Dart 3.13 formatter, so future
  `dart format` runs stop producing unrelated churn. No behaviour changes.

## Tooling: quieter test output

- The 69 `WARNING (drift)` lines are gone. The four test files that created a
  new `AppDatabase` per fake or harness now share one never-opened instance per
  file, matching the convention the other UI tests already followed; the single
  test that intentionally keeps two instances alive suppresses that warning
  locally.
- The 29 application-log warnings stay: they come from tests that assert
  failure and rejection paths, so removing them would weaken those tests.

## Known Limitations (Alpha)

- **Preview only.** Treat 0.3.0-alpha06 as a test build; use `0.2.1` for real
  contest logging.
- **No downgrade.** The database is migrated to schema v7. A `0.2.x` build may
  refuse to open a database written by this alpha, and QSOs logged here should
  be exported/backed up before switching back.
- **Old recordings cannot prove ownership.** Session replay requires the
  run-start header added in 0.3.0. A pending replay armed from a `0.2.1` or
  earlier recording is refused and the run starts from the current settings.
- **No online leaderboard.** Score submission and the server-side replay
  verification described in the design notes are not part of this alpha.
- **Installers are unsigned** (see below).
- Linux packages require glibc 2.35 or newer.

## Platforms and Installation

Only desktop platforms are packaged for release: Windows x64, macOS universal
(Apple Silicon and Intel), and Linux x86_64 (glibc 2.35+).

The installers are **unsigned**:

- **Windows** may warn about an unknown publisher — choose *More info → Run
  anyway*.
- **macOS** — right-click the app and choose *Open*, or allow it under
  *System Settings → Privacy & Security*.
