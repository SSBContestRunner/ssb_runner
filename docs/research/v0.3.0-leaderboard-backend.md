# v0.3.0 分数排行榜：后端选型与技术方案

> 调研时间：2026-10-28
> 调研范围：为桌面训练应用（Windows / macOS / Linux）增加「上传训练成绩 → 查看排名」能力；后端语言按建议采用 **Go**。
> 用户规模：**注册用户 < 1000**，日活预计 50–150。所有容量测算以此为前提。
> 前置约束：应用是**离线训练器**，成绩在本地生成；不存在实时对战、观战、多端同步需求。
> 说明：云厂商价格与免费额度变动频繁，正式落地前需按官方页面复核；本文不包含工期估算。

---

## 0. 结论（TL;DR）

1. **后端选型：Go 1.27 单体服务 + SQLite（`modernc.org/sqlite`，纯 Go、无 cgo），以 Docker 镜像交付；反向代理与 TLS 交给宿主机**。容器只监听 `127.0.0.1:8080`，由宿主机已有的 nginx / Traefik / 云负载均衡做 TLS 终止与转发；服务跑在一台 1–2 vCPU / 1–2 GB 的小型 VPS 上。1000 用户量级完全不需要 PostgreSQL、Redis、消息队列、K8s 或微服务。
2. **数据库用 SQLite 是刻意选择，不是妥协**：写入量峰值约 5–10 次/分钟，读多写少；开启 WAL 后单机可轻松承受每秒数百次写入。真正的上限在「备份/迁移/多实例」而不是吞吐，到那一步再换 PostgreSQL 即可，数据访问层保持可替换。
3. **身份用「匿名 player + 本地 token + callsign 展示名」**，不做密码、不做 OAuth。理由：这是训练榜，不是赛事认证；账号体系会显著增加找回、绑定、注销与合规成本。代价是 callsign 可被抢注，用「管理端重置 token」兜底即可。
4. **成绩可信度分层处理**：客户端上传**完整 QSO 明细**而不是只传总分；服务端做「结构校验 + 规则重算 + 合理性上限」三重校验，榜单默认只展示 `verified` 成绩。**离线应用无法做到完全防作弊**，目标是让作弊成本高于收益，而不是追求不可作弊。
5. **规则重算必须带 `ruleset_version`**：训练计分规则（`pointsFor`、乘数定义）未来会改，旧成绩要么按旧版本保留，要么在迁移时统一重算。否则同一榜单会混入不可比的分数。
6. **客户端改动很小**：官方 `http` + Drift 离线 outbox + 指数退避；赛后弹「上传成绩」而不是静默上传；首次上传前有隐私同意。
7. **成本**：一台小 VPS + 对象存储备份，约 **$0–6/月**；带宽与存储都远低于免费额度。真正的成本是**长期运维与作弊处理**，不是机器。
8. **主要未决问题**：服务器部署地区（关系到中国大陆用户的可达性）、是否需要账号/昵称、榜单是否按口音拆分、是否公开历史成绩。见 §10。

| 计分实现 | `lib/contest_type/` 下按赛事分策略类（WPX、CQ WW、ARRL DX、IARU、JIDX） | 服务端需要一份等价实现，或用 Dart 校验器 |

| 配置存储 | `shared_preferences` | player token / 上传开关 / 榜单缓存可放这里 |
| 发布渠道 | GitHub Releases（zip / dmg / deb / AppImage） | 版本号可直接随提交上报，用于规则与兼容性判断 |
| 用户量 | < 1000 | 所有设计都应为「一个人也能维护」服务 |

### 1.1 容量测算（为什么 SQLite 足够）

假设 1000 注册用户、日活 100、人均每天 3 局：

| 指标 | 估算 |
|---|---|
| 提交量 | 300 次/天 ≈ **0.0035 次/秒** 平均；晚间峰值按 20 倍计 ≈ **0.07 次/秒** |
| 榜单读取 | 每次赛后 + 主动刷新；峰值按 10 次/秒 计 |
| 单条成绩摘要 | 0.3–1 KB |
| 完整 QSO 明细 | 60–200 条 × 约 80 B ≈ **5–16 KB**（gzip 后 2–5 KB） |
| 年增量 | 约 11 万局 → 摘要 < 100 MB；若长期保留明细，约 0.5–2 GB/年 |
| 结论 | 单机 SQLite + 定期清理明细（见 §5.6）足够支撑数年 |

**注意**：真正会撑爆磁盘的是「无限期保留 QSO 明细」。建议明细只保留 30–90 天用于申诉/复核，之后只留聚合结果与哈希（§5.6）。

## 3. 后端方案对比

> 「适配度」按本项目（1000 用户、单人运维、需要规则重算）评估，不是通用排名。

| 方案 | 起步复杂度 | 运维负担 | 成本 | 厂商锁定 | 规则重算 | 1000 用户适配 | 结论 |
|---|---|---|---|---|---|---|---|
| **Go + SQLite（Docker 交付，推荐）** | 中 | 低（单容器 + 单文件库；反代归宿主机） | $0–6/月 | 无 | Go 内实现，完全可控 | ★★★★★ | **采用** |
| Go + PostgreSQL（托管） | 中 | 中（多一个托管服务） | 免费档/低 | 低 | 同上 | ★★★★ | 数据量或并发上来后再迁 |
| PocketBase（Go + SQLite） | **低** | 低 | 同上 | 低 | 需要写 Go hooks | ★★★★ | 快速原型备选；API 形态受框架约束 |
| Supabase（Postgres + RLS） | 低 | 低 | 免费档 | 中 | 需用 SQL/Edge Function 重写规则 | ★★★ | 「零后端」备选；规则重算仍要另写 |
| Cloudflare Workers + D1 | 中 | 极低 | 免费档 | 中高 | 需 JS/Rust 重写规则；CPU 时间受限 | ★★★ | 适合纯读榜单；写校验不顺手 |
| Firebase / Firestore | 低 | 极低 | 免费档 | **高** | 不适合关系型计分 | ★★ | 不采用 |
| Dart（shelf + sqlite3） | 中 | 低 | 同上 | 无 | **可直接复用现有计分代码** | ★★★★ | 值得认真考虑的「黑马」 |

### 3.1 为什么是 Go + SQLite

- **单镜像交付**：`CGO_ENABLED=0` 交叉编译出 linux/amd64、linux/arm64 的静态二进制，多阶段构建进 distroless 运行镜像；没有 libc、没有运行时、没有依赖地狱，交付物就是一个镜像 tag。
- **SQLite 的运维面最小**：备份就是复制/`VACUUM INTO` 一个文件；恢复就是换文件；不需要账号、连接池、VACUUM 调度服务。
- **写少读多，天然适合 WAL**：本项目每次训练结束才写一次，读榜单是几十行的索引扫描。
- **生态刚好**：`net/http`（Go 1.22+ 的 `ServeMux` 已支持方法+路径参数）、`modernc.org/sqlite`、`log/slog`、`golang.org/x/time/rate`、`golang-migrate`/`goose`。无需框架也能写清楚；用 `chi` 也只是为了中间件与路由分组。
- **不选 PostgreSQL 的理由**：不是性能，而是多一个需要备份、监控、升级、配防火墙的服务；1000 用户阶段这是净负担。
- **不选 PocketBase 的理由**：它把 auth、REST、admin UI 都包好了，但我们的核心是「自定义校验 + 自定义榜单 SQL」，落在它的 hook 体系里反而更绕；如果只想两天出原型，它是好选择。
- **Dart 后端的诱惑与代价**：服务端可直接 import 现有 `lib/contest_type` 做**逐位一致**的分数重算，`dart compile exe` 也能产出单文件。代价是要把共享模型抽成 package、服务端依赖树仍是 Flutter 生态、团队/招聘/示例更少。若「分数重算一致性」比「后端语言偏好」更重要，这是首选替代方案。

> 结论：**主方案 Go，规则重算用 Go 重写；若重写成本超预期，退化为「Go 服务 + Dart 校验 CLI 子进程」**，而不是放弃服务端校验。

## 4. 架构

```
Flutter desktop
  └─ ScoreSyncService (http + Drift outbox)
        │ HTTPS (JSON, gzip)
        ▼
   宿主机反向代理（TLS 终止、访问日志；nginx / Traefik / 云 LB，不属本项目）
        │ HTTP → 127.0.0.1:8080
        ▼
   Docker 容器：Go 单体服务  ── 內嵌 migrations / ruleset
        ├─ /v1/players
        ├─ /v1/runs         (校验 + 计分 + 入库)
        ├─ /v1/leaderboards
        └─ /admin (CLI, 非 HTTP)
        ▼
   SQLite (WAL，宿主机 bind mount)  ── Litestream / 每日 VACUUM INTO → 对象存储
```

### 4.1 代码结构建议

```
server/
  cmd/api/main.go
  internal/httpapi/      # 路由、中间件、DTO、错误映射
  internal/store/        # SQL、迁移、事务
  internal/scoring/      # 各赛事规则（与客户端规则同版本）
  internal/player/       # token 生成/校验、callsign 规范化
  internal/ratelimit/
  migrations/            # 内嵌 embed.FS
  deploy/
    Dockerfile           # 多阶段：golang:1.27 构建 → distroless/static 运行
    compose.yaml         # 单服务 api（可选加 litestream）
```

### 4.2 关键库

| 用途 | 选择 | 说明 |
|---|---|---|
| 路由 | `net/http` `ServeMux`（或 `chi`） | 标准库已够；chi 仅在需要分组中间件时引入 |
| SQLite 驱动 | `modernc.org/sqlite` | 纯 Go，`CGO_ENABLED=0` 可交叉编译 |
| 迁移 | `goose` 或 `golang-migrate`（embed） | 启动时自动迁移；单实例部署，无并发迁移问题 |
| 日志 | `log/slog`（JSON handler） | 结构化、无额外依赖 |
| 限流 | `golang.org/x/time/rate` | 进程内令牌桶，按 player/IP 维度 |
| 备份 | Litestream 或 cron `VACUUM INTO` | 见 §7.2 |
| 容器化 | 多阶段 `Dockerfile` + `compose.yaml` | 运行镜像用 `distroless/static`，非 root、`HEALTHCHECK` |

### 4.3 SQLite 配置基线

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA busy_timeout = 5000;
PRAGMA foreign_keys = ON;
```

- **单写连接**：Go 侧维护一个 `*sql.DB` 用于读（`MaxOpenConns` 可 >1），写操作串行化到一个专用连接或 `sync.Mutex`，避免 `SQLITE_BUSY` 抖动。
- 迁移与备份都通过同一把写锁，避免与在线写入交错。
- 数据库文件与 WAL/SHM 放在同一块本地磁盘；**不要放网络文件系统**。

## 5. 数据模型与接口

### 5.1 表结构（草案）

```sql
CREATE TABLE players (
  id            TEXT PRIMARY KEY,              -- uuidv7
  display_name  TEXT NOT NULL,                 -- callsign，原样展示
  name_norm     TEXT NOT NULL UNIQUE,          -- upper(trim(callsign))，防重
  token_hash    TEXT NOT NULL,                 -- sha256(token)，不存明文
  created_at    INTEGER NOT NULL,              -- unix ms
  last_seen_at  INTEGER NOT NULL,
  status        TEXT NOT NULL DEFAULT 'active' -- active | hidden | banned
);

CREATE TABLE runs (
  id              TEXT PRIMARY KEY,            -- 客户端 runId，天然幂等键
  player_id       TEXT NOT NULL REFERENCES players(id),
  contest_id      TEXT NOT NULL,
  mode_id         TEXT NOT NULL,
  difficulty_id   TEXT NOT NULL,
  ruleset_version INTEGER NOT NULL,
  question_seed   INTEGER NOT NULL,
  audio_seed      INTEGER NOT NULL,
  started_at      INTEGER NOT NULL,
  ended_at        INTEGER NOT NULL,
  qso_count       INTEGER NOT NULL,
  correct_count   INTEGER NOT NULL,
  callsign_errors INTEGER NOT NULL,
  exchange_errors INTEGER NOT NULL,
  score           INTEGER NOT NULL,
  verified        INTEGER NOT NULL,            -- 0/1
  reject_reason   TEXT,
  client_version  TEXT NOT NULL,
  payload_sha256  TEXT NOT NULL,               -- 同一 runId 重放校验
  detail_json     BLOB,                        -- gzip(QSO 明细)，按保留策略可空
  submitted_at    INTEGER NOT NULL
);

CREATE INDEX runs_board_idx
  ON runs(contest_id, mode_id, difficulty_id, verified, score DESC, ended_at ASC);
CREATE INDEX runs_player_idx ON runs(player_id, submitted_at DESC);
```

- 榜单查询只扫索引；1000 用户、十万级行数在毫秒级。
- `runs.id` 直接使用客户端 `runId`：**重复提交天然幂等**；同 id 不同 `payload_sha256` → `409 Conflict`。
- 名次用 `COUNT(*) + 1`（按排名键比较）即可；无需 Redis 或预计算表。行数上百万后再引入 `leaderboard_snapshots`。

### 5.2 排名键（必须固定）

```
ORDER BY score DESC, qsos_per_hour DESC, ended_at ASC, id ASC
```

- 先比分数；同分比速率（`qso_count / 时长`，服务端用 `started_at/ended_at` 计算，不信任客户端字段）；再比更早完成；最后用 `id` 兜底保证稳定。
- **榜单维度**：`contest_id + mode_id + difficulty_id + ruleset_version + 时间窗`。难度必须进维度——难度只改变音频环境（速度、噪声、QSB、pile-up 人数），不改计分公式，混在一起排名不公平。
- `ruleset_version` 也可先作为展示字段，不拆榜；但**分数重算与排序必须使用同一版本**，历史迁移时统一重算。建议直接进榜维度，避免后期不可比。

### 5.3 接口（`/v1`）

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| `POST` | `/v1/players` | 无 | 首次注册：提交 callsign，返回 `player_id` + `token`（仅此一次） |
| `GET` | `/v1/me` | Bearer | 返回昵称、上传开关、最佳成绩 |
| `POST` | `/v1/runs` | Bearer | 提交一局；幂等键 `runId` |
| `GET` | `/v1/runs/{id}` | Bearer | 自己的成绩详情（含校验状态） |
| `GET` | `/v1/leaderboards` | 无 | `contestId/modeId/difficultyId/window/limit/cursor` |
| `GET` | `/v1/leaderboards/mine` | Bearer | 自己在指定榜的名次 |
| `DELETE` | `/v1/me/runs` | Bearer | 删除自己的全部成绩（隐私合规） |

提交示例：

```json
{
  "runId": "018f2c1e-...",
  "contestId": "CQ-WPX",
  "modeId": "run",
  "difficultyId": "standard",
  "rulesetVersion": 1,
  "appVersion": "0.3.0+300000",
  "questionSeed": 123456,
  "audioSeed": 654321,
  "startedAt": "2026-10-28T12:00:00Z",
  "endedAt": "2026-10-28T12:30:00Z",
  "qsoCount": 120,
  "correctCount": 110,
  "callsignErrors": 6,
  "exchangeErrors": 4,
  "score": 12345,
  "qsos": [
    {
      "seq": 1,
      "callsign": "JA1ABC",
      "exchange": "001",
      "correctCallsign": "JA1ABC",
      "correctExchange": "001",
      "elapsedMs": 8123
    }
  ]
}
```

响应（只回必要字段，便于客户端显示名次）：

```json
{
  "runId": "018f2c1e-...",
  "status": "verified",
  "score": 12345,
  "rank": { "rank": 37, "total": 812, "window": "all-time" },
  "rejectReason": null,
  "duplicate": false
}
```

错误统一用 `application/problem+json`（RFC 9457）：

```json
{
  "type": "https://ssbrunner.com/errors/invalid-run",
  "title": "Run rejected",
  "status": 422,
  "detail": "score does not match recomputed value",
  "instance": "/v1/runs"
}
```

约束：

- 请求体上限 **256 KB**；`qsoCount` 与服务端时长上限（应用内 120 分钟）共同决定上限。
- 超时：读写 10 s；服务端总超时 15 s。
- 限流：单 player `POST /runs` 10 次/分钟；读接口 60 次/分钟/IP。超过返回 `429 + Retry-After`。
- `appVersion` 低于最低版本 → `400` + `problem+json`（`type: .../client-too-old`），客户端提示升级而不是静默失败。
- 服务端时间权威：`endedAt` 与服务器时间偏差 > 24 h 的成绩标 `unverified`（不直接拒绝，避免时区/时钟事故）。

### 5.4 榜单时间窗

- `all-time` / `last-7d` / `last-30d`；周榜以 **UTC 周一 00:00** 为界，避免本地时区造成边界争议。
- 周榜不新建表：`WHERE ended_at >= ?` + 同一索引即可；数据量大后再物化。

### 5.5 成绩可信度分层（防作弊）

威胁模型：客户端是本地的、开源的、可调试的；用户可以直接改数据库或伪造 HTTP 请求。裁判结论：

> **不可能证明一局成绩「真实发生过」**，只能证明它「自洽、符合规则、在人类可能范围内」。

| 层 | 内容 | 成本 | 拦截效果 |
|---|---|---|---|
| L0 身份与传输 | Bearer token、TLS、限流、请求体上限 | 低 | 挡脚本刷榜 |
| L1 结构校验 | 字段范围、`correctCount` 与明细一致、`elapsedMs` 单调、总时长与 `qsoCount` 的速率上限（如 ≤ 10 QSO/分钟）、分数不超过理论上限（`3 × qsoCount × 乘数上限`） | 低 | 挡「随手改个 10^9」 |
| **L2 规则重算** | 用服务端规则根据 **QSO 明细**重算 `points × multipliers`，与上报分数比对；不一致 → 拒绝 | 中 | 挡绝大多数伪造 |
| L3 可复现校验 | 用 `questionSeed` 重新生成题目，逐题比对答案 | 高 | 挡「自洽但编造」的明细 |
| L4 客户端签名 | 内嵌密钥 HMAC | 低 | **只是提高门槛**，密钥必然可被提取 |
| L5 人工/社区 | 异常成绩复核、举报、隐藏 | 低 | 兜底 |

**落地建议**：v1 做 L0 + L1 + L2；L3 作为后续选项（服务端复用 Dart 生成器或编译 Dart 校验器）；L4 不做，避免产生「我们已验证」的虚假安全感。

L2 需要移植的内容（工作量可控，5 个赛事）：

- `pointsFor`：按 DXCC/大洲/是否本实体判断 1/3/0 分（CQ WW、IARU、ARRL DX、JIDX 规则各不相同）；
- 乘数：前缀（WPX）、DXCC + 区（CQ WW / IARU）、州/省（ARRL DX）；
- **DXCC 前缀解析**：复用资源子模块中的 `cty.xml`，在 Go 侧实现同样的 callsign → entity/continent 查找；这是 L2 的主要风险点，需要与客户端一致的测试向量（可用真实成绩做对拍）。

对拍策略：从现有客户端导出一批「已知正确」的 QSO 集合与分数，作为服务端单测的黄金样本；每次规则变更同步更新。

### 5.6 QSO 明细保留策略

| 数据 | 保留期 | 理由 |
|---|---|---|
| 成绩摘要 + 分数 + 校验结果 | 永久 | 榜单与个人历史 |
| QSO 明细（gzip） | 30–90 天 | 申诉、复核、规则迁移对拍 |
| 原始请求体 | 不保存 | 无必要，且增加隐私面 |
| IP 地址 | 不落业务库（仅反向代理日志，7 天） | 合规最小化 |

到期任务用一条 `UPDATE runs SET detail_json = NULL WHERE submitted_at < ?` 清理，按批提交，避免长事务。

## 6. 客户端改造

### 6.1 新增依赖与模块

- `http: ^1.x`（官方维护，桌面三平台无额外原生依赖）。
- `lib/leaderboard/`：
  - `leaderboard_api.dart`：DTO + 错误映射 + 超时；
  - `score_sync_service.dart`：组装 `TrainingRunReview` + QSO 明细，执行上传；
  - `upload_queue.dart`：Drift 表 `pending_upload(run_id PK, payload_json, attempts, next_attempt_at, last_error)`；
  - `player_identity.dart`：`player_id / token / display_name`（`shared_preferences`）。

### 6.2 交互流程

1. 赛后 review 页出现 **Upload score**（默认不静默上传）。
2. 首次点击 → 隐私说明 + callsign 确认 → `POST /v1/players` → 本地保存 token。
3. 上传成功 → 显示「当前第 N 名 / 共 M 人」；失败 → 进入 outbox，设置页显示待上传数量。
4. 设置项：`Enable online leaderboard`（关闭后不注册、不上传，本地成绩不受影响）、`Hide my callsign`（榜单展示为 `Anonymous`，仍保留个人名次）。
5. 版本升级后：若 `rulesetVersion` 变化，旧成绩仍可查；客户端提交时使用当前版本。

### 6.3 重试与幂等

- 以 `runId` 为幂等键：网络超时后重试不会重复计分。
- 退避：1 min → 5 min → 15 min → 1 h → 6 h（上限），仅对 `408/429/5xx/网络错误` 重试；`4xx` 直接标记为永久失败并展示原因。
- 应用退出前不阻塞；下次启动继续。

### 6.4 测试

- `MockClient` 覆盖：成功、422、409 重复、429 退避、离线队列持久化、token 失效（401 → 重新注册？**不自动**，提示用户）。
- 用真实 v0.2.0 成绩样本做「客户端分数 = 服务端重算分数」的对拍测试（在服务端 CI 中跑）。

## 7. 部署与运维

### 7.1 部署形态

- 一台 1–2 vCPU / 1–2 GB VPS（Hetzner / Fly.io / Oracle 免费 ARM 均可，按可达性与备案要求选择）。
- **交付形态：单个 Docker 镜像 + 单服务 Compose**。仓库提供多阶段 `Dockerfile`（`golang:1.27` 构建 → `distroless/static` 运行，`CGO_ENABLED=0`）与 `compose.yaml`；镜像内只跑 API 进程。
- **反向代理与 TLS 由宿主机负责**，本项目不维护 Caddy/nginx 配置。容器只发布到 `127.0.0.1:8080`（或内网网段），由宿主机已有的反代做 TLS 终止与转发；`X-Forwarded-For` / `X-Forwarded-Proto` 由该层注入，服务端需配置可信代理网段白名单，否则忽略这两个头。
- 持久化：SQLite 文件与 WAL/SHM 通过 **bind mount** 挂到宿主机目录；不要放容器可写层，也不要放网络文件系统。
- 容器以非 root 运行，`HEALTHCHECK` 打 `/healthz`；日志走 stdout（`slog` JSON），由容器运行时收集。
- 升级即「停旧起新」，回滚即换回上一个镜像 tag；发布时保留最近 2–3 个 tag。
- 迁移在进程启动时执行；**只允许单实例**（SQLite 语义 + 迁移安全）。需要多实例时先迁 PostgreSQL。

### 7.2 备份与恢复

| 方案 | 说明 | 适用 |
|---|---|---|
| `sqlite3 db ".backup"` + cron | 最简单，停机无关 | 起步 |
| `VACUUM INTO` | 生成紧凑快照 | 每周 |
| Litestream | 持续复制 WAL 到 S3/R2 | 需要 RPO 分钟级时 |

- 备份必须**定期做恢复演练**：拉起临时容器 → 校验行数 → 删除。
- 保留：日备 7 份、周备 4 份、月备 3 份。

### 7.3 可观测性

- `/healthz`（进程 + DB ping）、`/readyz`。
- `slog` JSON：请求 ID、player_id、run_id、耗时、状态码；**不打 token、不打完整请求体**。
- 简易指标：提交数、拒绝数（按原因）、榜单延迟 p95、DB 文件大小。单机阶段可用 `expvar`/文本端点，无需 Prometheus。

### 7.4 成本

| 项 | 估算 |
|---|---|
| VPS | $0（Oracle 免费 ARM / Fly 免费档）– $6/月 |
| 备份对象存储 | 免费额度内（< 1 GB） |
| 域名 | 已有 `ssbrunner.com` |
| TLS | 宿主机反代（已有 nginx/Traefik/云 LB）+ 证书，$0 |
| **合计** | **$0–6/月** |

### 7.5 中国大陆可达性

- GitHub Releases 与部分海外 VPS 在大陆的延迟/可用性不稳定；如果目标用户主要在大陆：
  - 方案 A：阿里云/腾讯云轻量 + **ICP 备案**（`ssbrunner.com` 已备案则最简单）；
  - 方案 B：海外 VPS + Cloudflare 代理（可改善但非保证）；
  - 方案 C：客户端支持自定义 API 地址（高级设置），社区可自建。
- **这是产品决策，不是技术决策**，见 §10。

## 8. 备选方案评估细节

### 8.1 Supabase

- 优点：Postgres + 行级安全 + 自动 API + 控制台，MVP 最快；免费档对 1000 用户足够。
- 缺点：分数重算仍要写（Edge Function / SQL），规则代码与客户端双份维护；免费项目会休眠；数据出境与延迟。
- 适合：只想验证「有没有人愿意上传」。

### 8.2 PocketBase

- 优点：Go 编写、单二进制、SQLite、内置 auth/admin UI/实时订阅；扩展用 Go hook。
- 缺点：API 形状受框架约束；「QSO 明细校验 + 自定义排名键」要写不少 hook；升级需跟随上游。
- 适合：想用最少代码上线，且能接受框架风格。

### 8.3 Cloudflare Workers + D1

- 优点：全球边缘、免运维、免费额度大。
- 缺点：Go 不能直接跑（需 TinyGo/JS/Rust）；D1 写入与事务模型有限；规则重算需另写一份。
- 适合：榜单读多写少、且已有 Cloudflare 生态。

### 8.4 Dart 后端（shelf + sqlite3）

- 优点：**规则代码零重写**；DTO/模型与客户端共享；`dart compile exe` 单文件部署。
- 缺点：需要把共享逻辑抽成纯 Dart package（当前与 Flutter 强耦合）；服务端生态/示例少；团队若以 Go 为主则维护成本高。
- 适合：把「分数校验一致性」放在第一位，且不想维护两套规则。

## 10. 风险与待确认项

### 10.1 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 作弊 | 榜单失去意义 | L1+L2、Top N 人工复核、可隐藏/删除 |
| callsign 抢注 | 真实用户无法使用自己的呼号 | token + 管理端重置；展示名不等于身份认证 |
| 规则变更 | 新旧成绩不可比 | `ruleset_version` 进榜维度；迁移时统一重算 |
| 版权/许可 | 客户端 GPL-3.0，服务端如何授权 | 服务端**独立仓库**；若移植 GPL 代码则服务端也需 GPL；SaaS 不触发 GPL，若希望强制开源用 AGPL |
| 隐私/合规 | 呼号属于公开信息，但仍可能关联个人 | 最小化采集、可删除、隐私政策、日志脱敏 |
| 反代信任边界 | 宿主机反代配置不当会导致真实 IP/限流失真 | 文档固定「只发布到 127.0.0.1」；`X-Forwarded-*` 仅在可信代理网段内生效 |
| 运维中断 | 上传失败影响体验 | 客户端本地优先、outbox、榜单失败不阻塞训练 |
| 大陆可达性 | 上传成功率低 | 见 §7.5；客户端可配置 API 地址 |
| 成本误判 | 免费额度变化 | 容量与账单告警；SQLite 文件大小监控 |

### 10.2 待确认（会直接改变实现）

1. **部署地区**：海外 VPS（简单）还是大陆云 + 备案（可达性好）？
2. **身份**：匿名 player + 呼号展示（推荐），还是必须账号/邮箱？
3. **上传方式**：赛后询问（推荐）还是默认自动上传？
4. **榜单维度**：是否按口音拆分（固定口音功能上线后，口音会影响难度感知）？
5. **服务端开源**：独立仓库 MIT / AGPL / 闭源？
6. **是否需要历史成绩公开页**（个人主页 / 分享卡片）？
