# v0.3.0 分数上传：防作弊方案（威胁模型与分层设计）

> 调研时间：2026-10-29
> 关联文档：[v0.3.0 分数排行榜：后端选型与技术方案](./v0.3.0-leaderboard-backend.md)
> 前置事实：应用是**离线、开源、客户端本地计分**的桌面训练器；分数不是赛事认证，而是训练榜。
> 本文只讨论「上传分数」这一条链路的作弊与防护，不重复后端选型。

---

## 0. 结论（TL;DR）

1. **不要试图证明「这一局真的发生过」**。在开源桌面应用里，客户端、种子、答案生成器、呼号表全部可见，攻击者可以改数据库、改请求、编译修改版客户端。服务端最多只能证明：**这份明细在该种子下自洽、分数不超过理论上限、时间与行为落在人类可能范围**。
2. **防作弊的第一优先级不是加密，而是把权威从客户端搬到服务端**：服务端发种子、服务端定时长、服务端算分、服务端判有效。客户端上报的 `score / qsoCount / correctCount / startedAt / endedAt` 一律不作为事实。
3. **v0.3.0 推荐方案 A：服务端发「排位票」+ 赛后完整重放 + 固定时长分榜 + 统计风险分 + Top N 人工复核**。它能 100% 堵住「改总分、挑种子、重复刷同一局、改时长」这类**不写外挂就能做**的作弊，成本可控。
4. **方案 A 有一个诚实的残余风险**：懂代码的人可以本地模拟生成器，直接构造一份「全对、时间也合理」的明细在赛后提交。服务端重放无法分辨它和真人。要再提高门槛，只能上**方案 B：逐题在线会话**（服务端逐题下发音频、逐题收答案、服务端记时间），代价是排位模式必须全程在线、需要服务端音频管线。
5. **现有代码有 4 个必须先修的结构性漏洞**（不修，服务端重放也会继承）：
   - 种子可由用户锁定/指定，且生成完全确定，呼号表 46,039 条 → **可离线筛种子**挑「乘数多、呼号短、同洲少」的局；
   - 上传分数取的是 **raw score**，错误呼号也计分、也计乘数，且乘数用的是「输入的呼号」而不是「正确呼号」；
   - 时长可 0–120 分钟任意设置，而现有榜单维度里**没有 duration** → 60 分钟局天然碾压 10 分钟局；
   - 没有 run ticket / 会话绑定，`startedAt/endedAt/appVersion` 全由客户端上报（`appVersion` 目前甚至没被赋值）。
6. **排名的公平性本身就是防作弊的一部分**：原始分 `points × multipliers` 强依赖种子（前缀/ DXCC 分布）和台站所在大洲。建议用**种子归一化分**（实际分 ÷ 同一批题目的满分）作为主排名键，原始分只做展示。
7. **不要做**：内嵌 HMAC 密钥当防作弊、客户端反调试/反 Cheat Engine、TPM/远程证明、内核级反作弊。对 unsigned 桌面应用、< 1000 用户，这些是成本高、收益低，还会制造「我们已经验证过」的虚假安全感。

## 1. 现在的攻击面（基于代码事实）

### 1.1 四个结构性漏洞

| # | 事实 | 位置 | 后果 |
|---|---|---|---|

补充事实：

- 每个 QSO 只有 `utcInSeconds` 与事件日志里的 `elapsedMs`，**没有逐键时序**（[qso_table.dart](file:///Users/wafer-li/FlutterProjects/ssb_contest_runner/lib/db/table/qso_table.dart)、[event_log_table.dart](file:///Users/wafer-li/FlutterProjects/ssb_contest_runner/lib/db/table/event_log_table.dart)），所以行为检测目前只能做到「每 QSO 间隔」级别。
- 生成器用了 `dart:math Random`。Dart 官方不保证 `Random` 的实现跨 SDK 版本不变；服务端重放若依赖它，未来可能无法逐位复现。**长期应换成显式 PRNG（如 xorshift/PCG）并冻结版本**。
- `assets` 是 git submodule（`ssb_runner_assets`），呼号表/语音/`cty` 数据都有独立提交；服务端校验必须绑定**内容版本**，否则客户端换了呼号表就能改变题目序列。

## 2. 关键判断：哪些能防、哪些不能

### 2.1 信任边界

```
不可信                                      可信
客户端 UI / 本地 DB / 生成器 / 音频  ──►  服务端：种子、时长、题目、计分、时间、排名
```

只要客户端能读到自己生成的答案（现在就能），就有两种作弊路径：

1. **赛前/赛后离线解题**：拿到 seed → 本地生成全对答案 → 构造明细提交。
2. **赛中读取答案**：修改版客户端把正确呼号/交换直接显示或自动填入。

方案 A 只能堵住第 1 条的一部分（通过**服务端发票 + 限时交卷 + 墙钟校验**压缩「赛后解题」的时间窗），堵不住「赛中读取」。方案 B 才能把答案文本从客户端拿掉，让「赛中读取」退化为「对音频做语音识别」，成本陡增。

### 2.2 三层防护的成本/收益

| 层 | 手段 | 挡住什么 | 成本 | 结论 |
|---|---|---|---|---|
| 权威层 | 服务端发票、定种子、定时长、算分 | A1/A3/A4/A5/A6/A10 | 中 | **v0.3.0 必做** |
| 校验层 | 结构校验、重放、速率/上限 | A1/A2 的粗糙版本、A8/A9 | 中 | **v0.3.0 必做** |
| 检测层 | 统计风险分、Top N 复核、举报/封禁 | A2/A8/A11 | 低–中 | **v0.3.0 必做（轻量）** |
| 会话层 | 逐题在线下发音频/收答案 | A2/A7/A8 的实质门槛 | 高 | 方案 B，v0.4 视榜单重要性再上 |
| 客户端加固 | HMAC、混淆、反调试、TPM | 只提高逆向成本 | 高 | **不做** |

## 3. 方案 A（v0.3.0 推荐）：服务端权威 + 赛后重放

### 3.1 两种 run，彻底分开

| 类型 | 种子 | 时长 | 网络 | 能否上榜 |
|---|---|---|---|---|
| Practice run | 本地生成/用户可锁定/可回放 | 用户自选 | 可离线 | **不上主榜**；最多进「未验证/个人记录」 |
| Ranked run | **服务端发票时确定** | **服务端按票面固定** | 开跑与交卷需在线 | 通过校验才上主榜 |

> 这样既保留「离线训练器」的定位，又让排位榜有可信基线。用户想上榜时接受一次在线领票，训练本身仍可离线。

### 3.2 领票与交卷时序

```
客户端                                  服务端
  │  POST /v1/runs/tickets                │
  │  {contest, mode, difficulty,          │
  │   durationBucket}                     │
  │ ────────────────────────────────────► │ 检查：无未消费票、当日排位次数、
  │                                       │      配置合法、内容版本合法
  │                                       │ 从种子池选 seed，生成 ticketId/runId
  │ ◄──────────────────────────────────── │ {ticketId, runId, questionSeed,
  │                                       │  audioSeed, durationSeconds,
  │                                       │  issuedAt, expiresAt,
  │                                       │  contentVersion, generatorVersion,
  │                                       │  rulesetVersion}
  │                                       │
  │  用票面 seed/时长开跑（不允许改）      │
  │                                       │
  │  POST /v1/runs/{runId}/result         │
  │  {ticketId, events[]}                 │
  │ ────────────────────────────────────► │ 1) 票未消费、未过期、属于本人
  │                                       │ 2) 墙钟：now >= issuedAt + duration
  │                                       │ 3) 墙钟：now <= expiresAt
  │                                       │ 4) 事件数/顺序/间隔合法
  │                                       │ 5) 用 seed 重放，逐条核对
  │                                       │ 6) 服务端算分 + 风险分
  │ ◄──────────────────────────────────── │ {status, score, rank, rejectReason}
```

关键约束：

- **票在点击「开始排位」时同步申请**，不是提前批量发。这样 `issuedAt` 就是开跑时间，墙钟校验才有意义。
- **一票一局，消费即失效**；同一 player 同时最多 1 张未消费票；每日排位次数上限（建议 3 次），放弃也计数。
- **交卷窗口**：`expiresAt = issuedAt + duration + 180s`。超时即作废（排位模式不接受 outbox 隔夜重试；离线重试只适用于练习局）。
- **服务端校验墙钟**：`receivedAt - issuedAt >= duration` 且 `receivedAt - issuedAt <= duration + 180s`。只信服务端时间，不信客户端 `startedAt/endedAt`。
- **seed 去重**：同一 `(player, questionSeed)` 只接受一次有效排位，防「同一局反复交卷取最高」。
- **票面锁定** `contest/mode/difficulty/duration/stationCallsign/contentVersion/generatorVersion/rulesetVersion`；交卷时任何一项不一致直接拒绝。

### 3.3 服务端校验算法（伪代码）

```text
verify(ticket, events):
  assert ticket.status == "open"
  assert ticket.player_id == auth.player_id
  assert now >= ticket.issued_at + ticket.duration
  assert now <= ticket.expires_at

  truth = generate(
    seed          = ticket.question_seed,
    contest       = ticket.contest_id,
    mode          = ticket.mode_id,
    difficulty    = ticket.difficulty_id,
    content       = ticket.content_version,
    generator     = ticket.generator_version,
  )                                  # 与服务端内容包逐位一致

  assert events.len <= max_qso(ticket.duration, mode, difficulty)
  assert events.elapsed_ms strictly increasing
  assert last.elapsed_ms <= ticket.duration_ms + 1000

  # 允许漏题/超时跳过，但不允许乱序或超出已生成序列
  cursor = 0
  for e in events:
    idx = truth.match_forward(from=cursor, callsign=e.callsign_typed)
    if idx is None: reject("sequence-mismatch")
    cursor = idx + 1
    e.truth = truth[idx]
    # 音频至少播放过：用内容包里的 WAV 时长 × 播放速率 + 最小反应时间
    assert delta_ms(e) >= min_cycle_ms(e.truth, difficulty)

  # 只对「呼号 + 交换都对」的 QSO 计分；乘数只取正确呼号
  verified = [e for e in events if e.callsign_typed == e.truth.callsign
                              and e.exchange_typed == e.truth.exchange]
  score = recompute_score(verified, ticket.station_callsign, contest, ruleset)

  # 种子归一化：同一批已作答题目的满分
  max_score = recompute_score(all_attempted_as_correct, ...)
  efficiency = score / max_score

  flags = behavior_stats(events, truth, difficulty)
  if hard_violation: return "rejected"
  if flags:          return "quarantined"   # 不进主榜，等人工复核
  return "verified"
```

要点：

- **客户端上报的 `score`、`qsoCount`、`correctCount`、`startedAt`、`endedAt` 全部忽略**。事件条数由服务端数；正确数由服务端比对；时长由票面决定。
- **允许错题**：错呼号/错交换照常记录，只是不计分。服务端需要知道用户「输入了什么」，才能判断对错；不需要客户端上报「正确答案」。
- **漏题**：用户可能因超时跳过某个呼叫，事件日志允许缺口，但必须按生成顺序匹配（`match_forward`），不能跳回、不能重复。
- **最短 QSO 间隔**：`min_cycle_ms` 由服务端根据内容包中该呼号的 WAV 时长、交换音频、播放速率和固定延迟计算。它挡住「瞬间提交 1000 个 QSO」和「不等音频就自动填」；但挡不住「听了音频后用脚本填」。
- **风险分**：见 §3.7，只做隔离/复核，不自动封禁。

### 3.4 计分口径必须先修

服务端重放如果照抄客户端现有 `calculateScore`，会继承 S3 漏洞。建议在 v0.3.0 明确「排位分」口径，并让客户端本地 review 与服务端一致：

| 项 | 现在 | 建议（排位口径） |
|---|---|---|
| 哪些 QSO 计分 | 所有 QSO（含错呼号/错交换） | **仅呼号与交换都正确的 QSO** |
| 基分依据 | 输入的呼号（`qso.callsign`） | 正确的呼号（`truth.callsign`） |
| 乘数依据 | 输入的呼号前缀/DXCC | **正确呼号的前缀/DXCC** |
| 错呼号 | 仍可能加基分和乘数 | 0 分；按赛事规则可另记罚分，但不产生乘数 |
| 时长 | 客户端 `endedAt - startedAt` | 票面 `durationSeconds` |

这会改变本地「raw / verified」两个分数的语义。建议：

- UI 继续显示 raw（练习反馈）；
- 上传/排名只使用 **verified（严格口径）**；
- 在 review 页明确写「排位分只计完全正确的 QSO」，避免用户困惑。

### 3.5 时长与榜单维度

现有榜单维度是 `contest + mode + difficulty + ruleset + 时间窗`，**缺 duration**。必须补：

```
榜单键 = contest_id + mode_id + difficulty_id + duration_bucket
        + ruleset_version + generator_version + seed_pool_version
```

建议固定档位：**15 / 30 / 60 分钟**（或只做 30 分钟一个档）。不要让用户自由填 0–120 分钟；排位票由服务端按档位下发。

### 3.6 服务端种子池（公平性 + 防挑种子）

即使服务端发种子，随机种子之间仍有「前缀数量 / DXCC 分布 / 呼号长度 / 同洲比例」的运气差。做法：

1. 离线预生成候选 seed；
2. 用服务端生成器模拟 N 条题目，计算质量向量：`distinctPrefixes`、`DXCC 数`、`平均呼号长度`、`同洲 QSO 比例`、`重复呼号数`；
3. 只接受落在目标分位带（如 25–75 百分位）的 seed，入池；
4. 发票时从池中随机取；记录 `seed_pool_version`；
5. 规则/内容/生成器变更时重建池。

这样既减少「种子运气决定排名」，也让 A3 失去收益：挑不到异常种子。

### 3.7 风险分（统计检测，不自动封禁）

在只有「每 QSO 间隔」的数据下，可做的指标：

| 指标 | 人类特征 | 机器人特征 | 处理 |
|---|---|---|---|
| QSO 间隔均值 | 随呼号长度、难度变化 | 贴近 `min_cycle_ms` 或异常稳定 | 风险分 |
| 间隔变异系数 CV | 通常 > 0.2 | < 0.1 | 风险分 |
| 准确率 × 速度 | 高准确率通常伴随较低速度 | 100% 准确 + 高速度 | 隔离复核 |
| 重打/退格 | 有 | 常为 0 | 需要补日志字段后才能用 |
| 每字符键入间隔 | 有分布 | 极短/恒定 | 需要补日志字段后才能用 |
| 同日多账号/同 IP | 少 | 多 | 限流/人工 |

建议：

- 先上「硬约束」（最短间隔、最大 QSO 数、序列/时长），这些可以直接拒绝；
- 统计指标只产出 `risk_score` 与 `risk_flags`，进入 **quarantine**（不显示在主榜/显示为 pending），由人工复核；
- 误伤优先于漏放：训练榜不是奖金榜，宁可让可疑成绩 pending，也不要公开指控。

如果要让统计检测真正有效，客户端事件日志需要补：

```text
qsoIndex, eventType, elapsedMs,
typedCallsign, typedExchange,
correctionsCallsign, correctionsExchange,   // 退格/重打次数
keyIntervalsHistogram                       // 仅聚合，不上报原始按键内容
```

### 3.8 版本与内容一致性

| 版本 | 作用 | 建议 |
|---|---|---|
| `contentVersion` | 呼号表 + 语音包 + cty 数据的子模块提交/hash | 票面锁定；客户端启动时上报实际 hash；不一致拒绝排位 |
| `generatorVersion` | 题目生成算法（SessionRandom、呼号选择、交换生成） | 冻结；升级必须重建种子池与黄金样本 |
| `rulesetVersion` | 计分规则（pointsFor、乘数定义） | 进榜维度；历史成绩按旧版保留或统一重算 |
| `seedPoolVersion` | 种子池的筛选参数 | 记录，便于解释排名差异 |

> 现有 `SessionRandom` 依赖 `dart:math Random`。服务端重放要「逐位一致」，建议把 PRNG 换成显式实现（xorshift128+/PCG），并用黄金向量（N 个 seed × 前 M 条题目）锁死。否则 Dart SDK 升级后历史成绩可能无法复算。

## 4. 方案 B（加强版）：逐题在线会话

### 4.1 流程

```
客户端                                      服务端
  │ POST /v1/sessions                      │ 服务端选 seed，不把 seed 下发给客户端
  │ ◄──────────────────────────────────── │ sessionId, qsoCount=0
  │                                       │
  │ GET /v1/sessions/{id}/next             │ 服务端生成第 i 题
  │ ◄──────────────────────────────────── │ 音频（WAV/Opus，仅音频，不含文本）
  │  播放音频；用户输入                     │
  │ POST /v1/sessions/{id}/answer          │ 服务端记到达时间、比对truth
  │ {typedCallsign, typedExchange}         │ 立即返回 correct/incorrect
  │ ◄──────────────────────────────────── │ 正确文本（仅本题结束后返回，用于回看）
  │ ... 逐题循环 ...                        │
  │ POST /v1/sessions/{id}/finish          │ 服务端算分；不接受事后补交
```

### 4.2 为什么更强

- 客户端**不知道未来题目**，无法赛后离线构造整份明细；
- 服务端记录每题的**墙钟到达时间**，伪造 `elapsedMs` 没有意义；
- 修改版客户端即使读内存，也只能拿到当前题的音频，不能拿到答案文本（除非做 SSB 语音识别）；
- 天然支持「每题一次、不可回退」，不需要复杂的重放对齐。

### 4.3 代价

- 排位模式必须**全程在线**，断线即本局作废；
- 服务端需要**音频生成/缓存管线**（呼号表 + 语音包 + 口音/音标策略 + 拼接/混音），工作量明显大于赛后重放；
- 每题一次往返，网络差时体验下降；需要预生成下一题音频（但不提前下发文本）；
- 客户端要改成「服务端驱动」的会话状态机，和现有本地生成器/回放逻辑并存，复杂度高。

### 4.4 适用条件

只有当「排行榜的荣誉价值」高到值得投入时再上。对 < 1000 用户的训练榜，方案 A + 人工复核通常足够；方案 B 是榜单被脚本攻破后的升级路径。

## 5. 方案 C（不建议）：客户端加固

| 手段 | 为什么不做 |
|---|---|
| 内嵌 HMAC 密钥签名明细 | 应用开源，密钥可提取；只能防「事后改字节/串用」，不能防伪造；容易产生虚假安全感 |
| 代码混淆/加壳 | 提高逆向人力成本，但改变不了「客户端能看到答案」这一事实 |
| 反调试/检测 Cheat Engine | 三平台军备竞赛，维护成本高，且可绕过 |
| TPM/远程证明/设备指纹 | unsigned 桌面应用没有可信基线；隐私与合规成本高；用户量不值得 |
| 内核级反作弊 | 与「训练工具」定位冲突，安装/权限/杀软误报问题严重 |

> 结论：把预算花在**服务端权威 + 运营复核**，而不是客户端加固。

## 6. v0.3.0 落地清单

### P0（不做则榜单没有意义）

1. **修计分口径**：只对正确 QSO 计分，乘数只用正确呼号；客户端 review 与服务端一致。
2. **上传只传事件明细 + ticket**：不传 `score/qsoCount/correctCount` 作为事实；服务端算。
3. **排位票**：服务端发 seed、定 duration、定 content/generator/ruleset 版本；一票一局、限时交卷、墙钟校验。
4. **榜单维度补 duration**；固定 15/30/60 分钟档。
5. **硬校验**：序列匹配、事件数上限、最短 QSO 间隔、时长/配置一致。
6. **主榜只收 `verified`**；`quarantined` 不进主榜。

### P1（可与 v0.3.0 同期或紧随）

7. **完整重放**：服务端复用同一份生成器/计分器（推荐抽纯 Dart core + `dart compile exe` 校验器，确保逐位一致；Go 重写需黄金样本对拍）。
8. **种子池**：预筛平衡种子，发票从池中取。
9. **统计风险分**：CV、准确率×速度、最短间隔比的组合；只隔离不封禁。
10. **黄金样本**：从现有客户端导出「已知正确」的 QSO 集与分数，进 CI 对拍。

### P2

11. Top N 定期人工回放、举报入口、shadow ban、封禁/重置 token 的管理 CLI。
12. 明细保留 30–90 天用于申诉；到期清空 `detail_json`。

### 明确不做

- 把 HMAC 当防作弊；
- 客户端反调试/反内存修改；
- TPM/attestation；
- 内核反作弊。

## 7. 残余风险（必须接受并写进产品说明）

| 风险 | 方案 A 是否解决 | 说明 |
|---|---|---|
| 改总分/改时长/挑种子/重复交卷 | ✅ | 服务端权威 + 票 + 去重 |
| 构造「全对且时间合理」的明细 | ❌ | 开源生成器可本地复现；只能靠统计/人工 |
| 修改客户端直接显示答案 | ❌ | 方案 B 才能实质提高成本 |
| 脚本按音频节奏自动输入 | ❌（只能检测） | 最短间隔 + CV/准确率组合，误判与绕过都存在 |
| 多账号刷榜 | 部分 | 注册限流、聚类、人工封禁 |

**诚实的表述**：榜单上的 `verified` 应解释为「服务端按规则复算通过、时间与行为在合理范围」，而不是「证明本人亲手完成」。这句话应出现在上传前的隐私/规则说明里。

## 8. 需要拍板的问题（会直接改变实现）

1. **排位模式是否接受「开跑与交卷必须在线」？** 这是方案 A 的前提；若坚持完全离线，则离线局只能进「未验证」榜，主榜无法可信。
2. **主排名键用什么？**
   - 方案 A1：原始分（直观，但受种子/台站大洲影响大）；
   - 方案 A2（推荐）：种子归一化分 `score / maxScoreForAttempted`，再按作答量/正确数加权；
   - 方案 A3：固定时长内「正确 QSO 数」，分数只展示。
3. **时长档位**：只做 30 分钟，还是 15/30/60 三档？
4. **每日排位次数**：3 次？还是不限但同 seed 只算一次？
5. **是否公开历史明细/回放**（利于社区监督，也利于作弊者学习）？
6. **台站呼号与赛区**：是否按大洲/DXCC 分榜，还是用归一化分消除差异？
